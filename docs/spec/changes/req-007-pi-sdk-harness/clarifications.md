## Sessions

### Session 2026-09-12

- Q: Is the wrapping factory the only way a tool reaches the harness — including the pet-agent's own five tools, which touch no connector — or is there a second, trusted registration path for internal tools? → A: One path, no exceptions. Every tool given to any agent is produced by the factory, including `create_job`, `get_job_status`, `cancel_job`, `notify_user` and `ask_user`; tools that touch no external platform declare the internal origin instead of a connector and are evaluated like reads, so they cost a ledger record and a verdict rather than an exemption. The decisive argument is that a "trusted tool" category is a second registration path, and a second path is the bypass the factory exists to prevent (constitution principles II, III and VI). The consequence is that the factory's input type, not a review convention, is what makes an unwrapped tool unreachable: the harness is constructed from values only the factory can produce. (patched: proposal.md §What Changes; destined for `specs/agent` — "Tools reach the harness only through the wrapping factory" — and for the tool-wrapping contract)
- Q: When the gate holds a call, does the call block in place inside the running agent, or does the agent's turn end and resume later from a stored transcript? The spike measured both. → A: Both are used, and the durable one is the state. At the moment of the hold the transcript is written to the product's own store and the job moves to `waiting_approval`; the in-flight suspension is then an optimisation that avoids rebuilding the session when the decision arrives while the process is still alive. A decision that arrives after the process stopped, or after the waiting period expired, is served by rebuilding the session from the stored transcript. The consequence is that no guarantee rests on a promise held in memory, which is what lets the crash-recovery pass in `req-013-sqlite-ledger` classify a held call the same way it classifies any other unresolved call. (patched: proposal.md §What Changes; destined for `specs/approval`, model.md lifecycle, and the agent-session contract)
- Q: Transcripts are account-owned data under principle VII. Are they kept in the harness's own session files, or in the product's store alongside the ledger? → A: The product's store, as a replicated store in its own right: append-only, resolved by append-and-reconcile, erased on sign-out, and never the harness's own session file format. A store the product does not own cannot be given a retention rule, a replication descriptor, or a redaction pass, and `req-022-account-sync` already names a `transcripts` store in its examples. The consequence is that the harness is used as a stateless reasoning engine handed its messages at construction, which is also what makes a rebuilt session identical to a suspended one. (patched: proposal.md §Impact; destined for model.md entities and the agent-session contract)
- Q: The wrapper can fail three different ways before a tool runs — the ledger write fails, the gate refuses, the gate itself fails to evaluate. Does each fail the job, or does the agent get a result and carry on? → A: They are deliberately different. A refusal is a normal tool result: the agent receives a refusal result carrying the rule that fired, the refusal notice is attached to every later question in that job, and the agent may re-plan and report — a refused call is not a crash. A failed ledger write stops the call and fails the job, because principle III makes the record a precondition of the act. An evaluation failure is fail-closed in the same way the gate contract already defines, and it stops writes for the whole product rather than only this call, because an unreadable rule catalogue is indistinguishable from a tampered one. (patched: proposal.md §What Changes; destined for `specs/approval` — "A denied call returns to the agent as a refusal, not as a fault" — and for the tool-wrapping error matrix)
- Q: The PRD's provider clause names an interactive sign-in that does not exist on the embedded path. Should the product build one, or should the clause be corrected to what the embedded path actually offers? → A: Correct the clause; do not build a sign-in the harness does not have. The embedded path exposes a credential per provider and a custom endpoint descriptor for anything speaking the widely implemented completion protocol, both VERIFIED (`spikes/SP-6-pi-sdk/REPORT.md` §1 Q5). The product therefore offers exactly that: a provider profile the user creates in settings, whose credential lives in operating-system secure storage under `platform/contracts/secure-storage@0.1.0`, and no subscription is purchased. Role-to-model routing keeps its home in `req-017-provider-matrix`; this change specifies only the configuration surface it routes over. (patched: proposal.md §What Changes; destined for a MODIFIED requirement against `agent` — "Model provider and role routing are configured on the client" — and for the provider-profile contract)

## Assumptions

- The harness runs in the desktop client's main process, beside the connectors, the evaluator and the ledger writer, and no renderer window holds a session object. Assumed rather than asked because `req-009-rule-ir-hardgate` already places the evaluator there for the reason principle II gives, and a session that could be driven from a window would put the four-step order behind a message a compromised window could forge.
- One term is fixed for each concept across every artifact of this change: *agent harness* for the embedded third-party runtime, *harness session* for one agent instance together with its transcript, *transcript* for the ordered turns of that session, *wrapping factory* for the function that produces a wrapped tool, *tool implementation* for the executable the factory holds privately, and *suspension point* for the held call a run stops at. The spike source is bilingual and uses several names per concept; the artifacts do not inherit that.
- The composer applies one product-wide minimum image dimension of 14 pixels in either direction, rather than a floor that varies by provider. Assumed rather than asked because the floor was measured against one vision endpoint (`spikes/SP-6-pi-sdk/REPORT.md#4-rui-ro-moi-phat-hien`), an image smaller than that carries nothing a model could read, and a per-provider floor would make the composer's refusal depend on a setting the user changes elsewhere. A provider that demands more is handled by `req-017-provider-matrix` raising the floor, not by this change branching.
- The harness's default coding tools are never installed and never registered. The spike established that the embedded runtime loads no tools at all unless given them (`spikes/SP-6-pi-sdk/REPORT.md` §1 Q1), so this is the absence of an action rather than a suppression to implement, and the requirement exists to keep it that way.
- Token usage is read from the session rather than estimated. The spike retrieved it at both the turn level and the transcript level (`spikes/SP-6-pi-sdk/REPORT.md` §1 Q7); this change records that the session surface exposes it and leaves what is displayed and what it costs to `req-017-provider-matrix`, which owns cost presentation.
