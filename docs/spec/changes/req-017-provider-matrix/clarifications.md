## Sessions

### Session 2026-09-12

- Q: The living `pet` requirement "All pet-visible text originates from the pet-agent" forbids hardcoded strings on the pet surface, and the measured remedy for the two-second commitment is exactly that — a locally held persona line shown before any model has answered. Which gives way? → A: Neither is dropped; the requirement is narrowed to what it was protecting. The acknowledgement line set is a **persona asset**, authored and localised as part of the persona specification, and it is admitted on one condition: an acknowledgement states receipt and nothing else — it names no entity from the command, asserts no understanding of it, and promises no outcome. Everything that carries meaning about the request — results, errors, questions, refusals — stays model-generated exactly as the requirement says today. The decisive argument is that FR-PET-10 exists so the pet has one voice and so the product cannot smuggle system notifications past the persona; a receipt line that says nothing about the content does neither. The consequence is that the two-second commitment stops depending on a network at all, and the rabbit hole the proposal named — an acknowledgement that appears to confirm comprehension — is closed by the content rule rather than by hoping the copy stays vague. (patched: proposal.md §What Changes; destined for `specs/pet` — MODIFIED "All pet-visible text originates from the pet-agent" and ADDED "The pet acknowledges a handed-over command before any model answers" — and for `specs/uix`)
- Q: Two roles have a model forbidden by measurement — the cheap model silently downgrades rules (`req-004-rule-elicitation`) and the strong model is required for undo (`req-010-undo-agent`). The user brings their own provider, and the product cannot tell whether a model it has never seen is strong. How does the matrix express a prohibition it cannot evaluate? → A: In two layers, and it never pretends the second is the first. The **enforced** layer is mechanically checkable: a role declares the capabilities its requests need — image input for the pet's image slot, tool calling for the worker — and an assignment to a model whose profile does not declare them is refused at the moment it is made, because that failure is a protocol fact the product can observe. The **advisory** layer covers strength: for the built-in profiles the product ships, the defaults follow the measured matrix and the model measured as unsafe for a role is not offered for it; for a model the user typed in, the product states at the point of assignment that it holds no measurement for this model in this role and names what was measured, then accepts the user's choice. The decisive argument is the constitution's evidence discipline — claiming to enforce a strength rule the product cannot evaluate would be an assertion without evidence built into the product itself. The consequence is that a single-model user is never locked out, and a user who overrides a measured default has been told what they are overriding. (patched: proposal.md §What Changes; destined for `specs/agent` and the role-routing contract)
- Q: Is image handling a routing slot of its own, or the pet role branching on whether an image is attached? → A: A slot of its own, inside a closed catalogue of six: pet text, pet image, worker, rule elicitation, undo, risk judge. Routing resolves from the pair (role, input shape) and never from the model's own report of what it can do. The decisive argument is that the alternative — one pet slot that switches models when an image appears — hides a model change inside a request the user did not configure, and it gives the composer nothing to inspect when it has to decide whether the attachment control can be enabled at all. As a slot, the image route is a thing the user can see unassigned, assign, and be warned about; as a branch it is invisible until it fails. The consequence is that a user with one text-only model has five roles assigned and one visibly unassigned, which is the state the composer reads to disable attachment. (patched: proposal.md §What Changes; destined for model.md entities and the role-routing contract)
- Q: Job detail is to show token usage and estimated cost. Every figure in the spike comes from one provider's price list at one moment. Where does the product get a price for a model the user configured? → A: From the user, or not at all. A profile may carry an optional price per model — input and output unit prices in a stated currency — which the user enters and the product never invents; when it is absent, job detail shows the token counts and states that no price is configured, rather than showing a number derived from a table the product shipped. The decisive argument is that a shipped price table is a claim about a third party's commercial terms that goes stale silently, and a stale cost figure on a job page is worse than no figure, because the user has no way to see that it is wrong. The consequence is that the risk this change exists to close — a user surprised by their own provider bill — is closed by showing real usage always and a cost only when it rests on a number the user supplied. Display belongs to the job detail page, which is owned by the `app` capability; `app` is therefore added to the proposal's Modified Capabilities. (patched: proposal.md §What Changes and §Capabilities; destined for `specs/app`, `specs/agent` and the usage-accounting contract)
- Q: Does the routing table replicate with the account? Provider credentials deliberately do not (`agent/contracts/provider-profile@0.1.0`), so a second device would hold assignments pointing at a profile whose credential is absent. → A: The table replicates; the credential does not; and the gap is reported rather than routed around. Assignments are configuration, and principle VII makes configuration account-owned, so signing in on a new machine brings the user's model choices with it — which is the whole point, because reconstructing six assignments by hand is exactly the setup burden the principle exists to remove. A role pointing at a profile whose credential is missing on this device produces the system card `provider-profile` already defines for that condition, naming the profile and the roles affected, and the product does not silently retarget the role to another profile that happens to have a credential. The decisive argument is that silent retargeting would run the user's rule elicitation on a model they never chose for it, which is precisely the failure `req-004-rule-elicitation` measured. (patched: proposal.md §Impact; destined for `specs/agent` and the role-routing contract)

## Assumptions

- A response that completes with no content and no error is a failure, not an empty answer. The spike observed it as the shape of the silent vision drop (`spikes/SP-17-provider-matrix/REPORT.md#4-rui-ro-moi-phat-hien`), and no legitimate turn in this product produces it: every model request in the product is made because something needs an answer. Assumed rather than asked because treating it as success is the defect the finding describes, and there is no product decision on the other side of it.
- One term is fixed for each concept across every artifact of this change: *role* for a routing slot, *assignment* for the pair of a profile and a model bound to a role, *routing table* for the whole set of assignments, *capability requirement* for what a role's requests need a model to declare, *price book* for the user-supplied unit prices, and *usage record* for the tokens one request consumed. Model strength is referred to as *measured suitability for a role* and never as a property of a model; vendor model identifiers appear in evidence citations and in `verification.md`, and in no requirement.
- Capability checking happens in the main process, and a window learns only the outcome. The composer is told whether images may be attached and why not; it is never told which profile or model the answer came from, because a window that could compute the routing decision could also disagree with it, and the request is made on the other side of that boundary anyway. Assumed rather than asked because `req-007-pi-sdk-harness` already places the harness and profile resolution in the main process for the reason principle II gives.
- The measured cost figures are evidence about a structure, not a price the product quotes. The monthly figure of $0.167 at fifteen jobs (`spikes/SP-17-provider-matrix/REPORT.md#0-ket-luan`) belongs to `verification.md` as the threshold the role split must keep in range when re-measured; it appears in no requirement and on no product surface, because the user's own provider and prices determine what they pay.
- Latency is a property of an assignment, not of the product. The acknowledgement requirement is written so that no model latency can breach it; the rest of the product's timing commitments continue to be measured against the assignment in force, and a user who points the worker role at a slow model gets a slower worker. Assumed rather than asked because the alternative — the product refusing assignments whose latency it has not measured — would forbid every model the user brings.
