## Sessions

### Session 2026-09-12
- Q: Should an approval rule identify what it protects using Notion's own words — database, page, block — or using neutral object types that each connector declares in its own manifest file? → A: Neutral now. A rule targets a connector, an object type, an object id and an ancestor chain; the object types are values the connector manifest declares, so Notion's database, page and block stop being part of the rule format itself. The predicate semantics the spike measured are unchanged; only the names are. (patched: proposal.md §What Changes; destined for model.md entities and the rule representation contract)
- Q: When the user switches the approval mode to `off`, should the rules the user wrote themselves stop applying, or should a rule the user wrote as an outright refusal still refuse? → A: A refusal still refuses. Mode `off` removes the waiting, not the boundary: user rules whose verdict is refuse are evaluated in every mode alongside the hardline list, and only approval-type user rules fall silent. This is stricter than the behaviour the spike ran, where mode `off` skipped the whole user catalogue. (patched: proposal.md §What Changes; destined for a MODIFIED requirement against `approval` — "Approval mode `off` removes waiting but not recording")
- Q: Some rules count things — "stop after more than five writes in one job", "stop after ten new tasks in a day". Where should those running counts live, and what happens to them when the app restarts or when the user works on a second computer? → A: They are derived from the account's own append-only ledger records rather than held in session memory, so a restart does not reset a threshold and a second signed-in device counts the same account's writes. The consequence is that the evaluation path now reads accumulated state, which the measured 0.48 ms p99 did not include; the latency budget must be re-established over the real read. (patched: proposal.md §What Changes and §Impact; destined for model.md entities and invariants, design.md, and the verification thresholds)
- Q: In the measured run the agent tried to talk the user into doing a blocked action by hand and was caught by a fixed list of phrases; a phrase list will not survive a rewording or a second language, so what should the product do instead? → A: The gate stops judging free text altogether. Once it refuses or holds an operation within a job, the product itself attaches that refusal — the operation, the target and the rule that fired — to every question the agent subsequently asks the user in that job, so the user cannot be asked to act without seeing what was refused. The consequence is that adversarial case A-14 is re-scored from blocked to disclosed, and the zero-leakage claim must be restated for that one case. (patched: proposal.md §What Changes and §Assumptions; destined for a requirement in the `approval` spec delta and for design.md)
- Q: When two of the user's own rules both match the same operation and disagree — one says stop, the other says allow — which one should win, and who decides that order? → A: The strictest verdict wins, always: refuse beats stop-and-ask beats allow. User rules carry no priority number, so neither the model that compiles a rule nor a mis-ordered list can weaken one. An exception is expressed inside the rule that grants it, using the representation's own negation, rather than as a separate allow entry layered over a stopping rule; and a permanent allowlist entry therefore covers only operations that no stopping rule matches. (patched: proposal.md §What Changes; destined for model.md invariants and a MODIFIED requirement against `approval` — "Approval offers four decision levels")

## Assumptions

- The evaluator runs in the desktop client's main process, alongside the connectors and the ledger writer, and is not reachable from any renderer window. This was assumed rather than asked because principle II requires the gate to sit between the agent and the connector, and the connector calls and ledger writes already live there; placing it anywhere a renderer could reach would put the gate behind an inter-process message that a compromised window could forge.
- A rule catalogue that cannot be read, or that fails validation against the rule representation schema, causes every write operation to be refused until it is repaired, rather than being treated as an empty catalogue. Assumed from the fail-closed discipline that principles II and III already impose on the ledger write path; an unreadable catalogue is indistinguishable from one that has been tampered with.
- One term is fixed for each concept across all artifacts of this change: *rule representation* for the stored format, *evaluator* for the component that decides, the verdicts *allow*, *hold for approval* and *refuse*, *hardline rule* for the built-in refusals, and *scoped approval* for the job-bound grant. The spike source uses several names per concept and is bilingual; the artifacts do not inherit that.
- The frozen adversarial corpus at `spikes/fixtures/sp8-adversarial.md` remains the regression gate, as the proposal already states, and gains the connector-neutral and ledger-derived variants of each case rather than replacing them.
